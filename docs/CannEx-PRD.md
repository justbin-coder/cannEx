# CannEx — CANN 开发者学习导师 Agent

> **一句话定位**：面向 Ascend C 算子开发者的 AI 学习导师，基于问题驱动的分级教学引导，帮助开发者高效掌握关键概念、避免常见踩坑、加速从入门到精通。

---

## 一、产品定义

### 1.1 产品名称

**CannEx**（CANN + Expert/Explore）

### 1.2 产品形态

以 Skill Pack 形式运行在 Claude Code / OpenCode / Codex 等 AI Agent 前端上，对外呈现为完整的 Agent 服务能力。

- **Phase 1 交付**：CLI 端 Skill 体系（即时可用）
- **Phase 2 规划**：Web 端服务（扩大覆盖面）

### 1.3 核心价值主张

| 维度 | 传统方式 | CannEx |
|------|---------|--------|
| 学习路径 | 700 页文档自行摸索 | 自适应引导，按问题复杂度调整深度 |
| 踩坑成本 | 遇到问题再搜索/问人 | 前置预警 + 故障诊断 + 踩坑速查 |
| 概念理解 | 阅读抽象定义 | 类比桥接 + 溯源官方文档 |
| 代码样例 | 从 50+ 仓中自行翻找 | 按需求检索匹配的完整代码样例 |

### 1.4 与现有能力的关系

CannEx 是**学习导师**，不是自动编码 Copilot。

```
CannEx (教学引导)           Ascend C Auto-Dev Skill (自动开发)
├── 目标：让开发者学会        ├── 目标：帮开发者完成任务
├── 交互：问答 + 引导         ├── 交互：指令 → 代码生成
└── 输出：知识 + 能力提升      └── 输出：可运行的算子代码

关系：互补，不耦合。开发者先用 CannEx 学习概念，再用 Auto-Dev 完成任务。
```

## 二、问题洞察

### 2.1 开发者学习痛点

**痛点 1：不知道全景，无法定位自己**

> "算子开发是干什么的？我用 PyTorch 直接推理不行吗？"

新开发者缺乏算子在 AI 部署链路中的位置认知，不知道算子有哪些类型、自己该从哪里开始。

**痛点 2：文档厚但不分级，信息过载**

> "文档 700 页，Pipeline 编程范式、SIMD、SIMT、静态 Tensor……我应该先学哪个？"

官方文档面向所有层级，没有按能力阶梯组织。初学者一开始就被暴露在高级概念中，容易放弃。

**痛点 3：概念到实践的鸿沟**

> "有没有先计算 Cube 再计算 Vector 的较好的例子？"

开发者理解了概念（如 Cube+Vector 融合），但找不到完整、可运行、有注释的参考实现。

**痛点 4：踩坑无预警**

常见问题如 DataCopy 的 burst 对齐要求、跨平台 UB 大小差异、数据类型限制等——文档中分散在不同章节，开发者往往是踩到了才知道。

**痛点 5：不知道"好"的标准**

> "我的算子能跑了，但性能怎么样算合格？"

缺乏性能基线参考和优化方向指引。

### 2.2 现有方案的不足

| 方案 | 不足 |
|------|------|
| 官方文档 | 全面但不分级，缺学习路径引导 |
| 线下培训 | 周期长、覆盖人数有限、无法按需学习 |
| 社区问答 | 碎片化、质量参差、搜索效率低 |
| 通用 AI 助手 | 底座大模型对 Ascend C 知识语料极少，回答不可靠 |
| Coding Copilot | 解决"怎么写"，不解决"怎么学"和"为什么这么写" |

## 三、用户画像

### 3.1 设计原则：问题驱动画像

传统画像用静态标签定义（"有 C++ 基础"），CannEx 用**开发者真实会问的问题**定义每个层级。问题本身就是最精准的能力信号，也直接映射到教学内容。

### 3.2 Beginner — "我连问题空间都还没看清"

**典型身份**：
- AI 算法工程师（熟悉 PyTorch，日常 `model.forward()` 就能跑）
- 科班 C++ 开发者（写过多线程服务端，从未接触 GPU/NPU 编程）
- 高校研究生（导师要求"把模型跑在昇腾上"）

**典型问题集**：

| # | 真实问题 | 认知缺口 | 教学应答策略 |
|---|---------|---------|-----------|
| B1 | "算子开发是干什么的？我用 PyTorch 直接推理不行吗？" | 不理解算子在部署链路中的位置 | 画全景图：模型→框架→算子→硬件 |
| B2 | "Ascend C 和 CUDA 什么关系？要先学 CUDA 吗？" | 不确定学习路径依赖 | 明确"不需要"，用 CUDA 做类比桥梁 |
| B3 | "算子有多少种？我应该先学哪种？" | 缺分类全景 | 给四类分类图，明确从纯 Vector 开始 |
| B4 | "TPipe、TQue 是什么？为什么不能像写普通 C++ 一样？" | 不理解异构编程的数据搬运本质 | 用"厨房比喻"：冰箱(GM)→案板(UB)→炒锅(计算)→盘子(GM) |
| B5 | "编译通过了但结果不对，怎么调试？" | 不知道调试工具和方法 | 引导 CPU 模式对比、printf 调试、数据 dump |
| B6 | "什么是 Tiling？我的数据量很小需要吗？" | 不理解硬件缓存容量约束 | 从 UB 大小出发：数据放不进 UB，必须分块搬运 |

**他们需要先建立的认知框架——算子分类全景**：

```
大模型算子分类（按计算单元）
│
├── 1. 纯 Vector 算子（元素级计算）
│   ├── 代表：Add, ReLU, Sigmoid, Abs, Cast
│   ├── 特征：逐元素操作，无数据依赖，最简单
│   └── 入门价值：★★★★★（第一个算子必须从这里开始）
│
├── 2. Vector 融合算子（多个 Vector 操作串联）
│   ├── 代表：LayerNorm, RMSNorm, SiLU+Mul, GELU
│   ├── 特征：多步 Vector 计算融合，减少 GM 读写
│   └── 入门价值：★★★★（理解"为什么要融合"的最佳切入点）
│
├── 3. 纯 Cube 算子（矩阵乘法）
│   ├── 代表：MatMul, BatchMatMul, GEMM
│   ├── 特征：调用 Cube 硬件单元，L1→L0 两级缓存
│   └── 入门价值：★★★（Matmul API 封装度高，初期用高阶 API 即可）
│
└── 4. Cube + Vector 融合算子（矩阵乘 + 后处理）
    ├── 代表：MatMul+ReLU, MatMul+LeakyReLU, Attention
    ├── 特征：Cube 输出(CO2) 直接流入 Vector(VECIN)，不回 GM
    └── 入门价值：★★（最复杂，需理解两套计算单元的协作）
```

**核心恐惧**：
- "文档 700 页，该从哪里开始？"
- "代码能编译但结果不对，完全不知道怎么调试"
- "CUDA 我也不会，是不是要先学 CUDA？"

**教学策略**：
- 先 Why（为什么需要算子开发），再 What（算子分类），最后 How（怎么写）
- 用 PyTorch 算子 → Ascend C 算子的类比桥接认知
- 第一个里程碑：跑通 Add 算子（纯 Vector），建立信心
- 严格控制信息量：一次只教一个概念

### 3.3 Intermediate — "我能跑通，但不知道怎么跑好"

**典型身份**：
- 已写过 1-3 个 Vector 算子，通过编译和正确性验证
- 开始接触 Cube 算子或被要求优化性能
- 参与团队项目，需要写"能上线"的算子

**典型问题集**：

| # | 真实问题 | 认知缺口 | 教学应答策略 |
|---|---------|---------|-----------|
| I1 | "Double Buffer 开了但性能没提升，为什么？" | 不会分析流水瓶颈 | 教流水时序分析：画时间轴，判断瓶颈在 Compute 还是 CopyIn |
| I2 | "UB 有 256KB，3 个 tensor 每个分多少？" | 不会做 UB 内存规划 | 教内存规划公式：对齐(32B) × Double Buffer(×2) × 预留 |
| I3 | "LayerNorm 融合的中间变量怎么处理？" | 不会设计 Vector 融合数据流 | 教 VECCALC 临时空间使用，画融合数据流图 |
| I4 | "Matmul 的 Tiling 参数怎么算？" | 不理解多维 Tiling 约束 | 从 L1/L0 容量反推，给计算模板 |
| I5 | "Atlas A2 上能跑但 Atlas 300 上报错" | 不理解跨平台差异 | 引导检查 UB 大小、数据类型支持、指令集差异 |

**核心困境**：
- "算子结果对了但比 PyTorch CPU 版还慢，怎么优化？"
- "别人代码里有 SetTail、SetMask，不知道干什么的"

**教学策略**：
- 从"你的算子为什么慢"开始，用性能数据驱动学习动机
- 教性能分析心智模型：计算 bound vs 搬运 bound → 对症优化
- UB 内存规划作为核心技能
- 每个概念配对应的代码样例（通过 :examples 检索）

### 3.4 Expert — "我要逼近硬件理论峰值"

**典型身份**：
- 能独立完成各类算子开发，包括融合算子
- 追求硬件利用率 80%+，或解决极端性能需求
- 算子库团队核心开发者，或 CUDA 迁移过来的高性能计算工程师

**典型问题集**：

| # | 真实问题 | 认知缺口 | 教学应答策略 |
|---|---------|---------|-----------|
| E1 | "有没有先计算 Cube 再计算 Vector 的较好的例子？" | 缺 Cube+Vector 融合实现参考 | 给 MatMul+LeakyReLU 完整示例，重点讲 CO2→VECIN 衔接 |
| E2 | "静态 Tensor 比 TPipe 能快多少？什么场景值得切？" | 不确定优化收益 | 给对比数据，明确"kernel 占总时间 >30% 时值得" |
| E3 | "L0A 的 Bank 冲突怎么判断？" | 缺微架构 Bank 分布知识 | Phase 2 RAG 支撑 |
| E4 | "CANN 9.0 的 DataCopy 和 8.0 行为有差异吗？" | 跨版本兼容问题 | Phase 2 版本差异索引 |
| E5 | "GQA Attention 利用率卡在 70%，瓶颈在哪？" | 需 profiling + 微架构知识 | 引导 msprof 工具 + Cube/Vector 利用率分析 |

**教学策略**：
- 不需要引导式教学，而是按需精准查询 + 深度讨论
- Phase 2 RAG 在此层级才真正必要
- :pitfalls 对 Expert 最有价值：高级用法的隐式约束

### 3.5 跨层级认知阶梯

```
Expert    "如何逼近理论峰值？"
  ↑        需要：微架构细节、API 精确语义、性能 profiling
  │
Intermediate  "如何从能跑到跑好？"
  ↑        需要：性能模型、内存规划、Tiling 策略
  │
Beginner  "这是什么？为什么需要？从哪开始？"
           需要：全景认知、类比桥接、信心建立
```

**毕业标准**（用于学习进度参考）：

| 晋级路径 | 毕业标准 |
|---------|---------|
| Beginner → Intermediate | 独立完成一个 Vector 融合算子（如 LeakyReLU），通过正确性验证，能解释 Pipeline 三阶段在自己代码中的体现 |
| Intermediate → Expert | 独立完成一个 Cube+Vector 融合算子，UB 内存规划有据可查，性能达到基线的 60%+ |

## 四、产品架构

### 4.1 整体架构

```
ascend-c (统一入口 Skill)
│
├── 意图识别 + 分发（自然语言 / 显式子命令）
│
├── :learn     — 概念教学 + 方法论引导
├── :examples  — 代码样例检索
└── :pitfalls  — 故障诊断 + 踩坑预警
```

**层级自适应**：不做显式诊断定级，根据用户问题本身的复杂度自适应回答深度：
- "算子是什么" → 从全景图讲起，用类比，控制信息量
- "Double Buffer 没提速" → 直接讲流水瓶颈分析
- "L0A Bank 冲突" → 给微架构级回答

### 4.2 三个子模块

#### :learn — 概念教学 + 方法论引导

覆盖六大教学能力：硬件架构认知、算子开发范式、精度对齐方法论、性能优化方法论、前置知识桥接、版本/硬件适配。

根据用户问题自动判断意图，选择应答模式：

| 用户意图 | 识别信号 | 应答模式 |
|---------|---------|---------|
| "什么是 X？" | 概念类提问 | 概念解释（引用知识页 + 类比桥接） |
| "X 怎么用？" | 用法类提问 | 方法论引导（知识页 + 官方文档溯源） |
| "有没有 X 的例子？" | 示例需求 | 转发到 :examples |
| "X 报错了" | 故障排查 | 转发到 :pitfalls |

#### :examples — 代码样例检索

根据开发者需求，从知识库中检索匹配的完整代码样例：
- 按算子类型、计算单元（Vector/Cube/融合）、难度匹配
- 代码原样展示（不做任何修改），用独立文字说明关键逻辑
- 标注来源仓库路径和适用版本
- 同时支持从 50+ 算子仓知识页中检索仓库级信息

#### :pitfalls — 故障诊断 + 踩坑预警

**来源与引用规范**：

| 来源类型 | 示例 | 引用格式 |
|---------|------|---------|
| 官方文档明确记载 | "DataCopy 要求 32 字节对齐" | `[来源: 官方开发指南 §4.3.2]` |
| 社区 Issues 闭环 | "Atlas A2 不支持 int4 的 Add" | `[来源: gitee.com/ascend/xxx/issues/123]` |
| 内部积累验证 | "Double Buffer depth=3 在某些场景更优" | `[来源: 内部实测 2026-04]` |
| 文档推断 + 实测 | "L0A 每个 Bank 16KB，交错步长应为..." | `[推断: 基于内存映射表 + 官方 Bank 冲突说明推导]` |

### 4.4 知识支撑体系

#### 三层架构（Phase 1）

```
┌─────────────────────────────────────────────────────┐
│ Layer 1: Skill 文件                                  │
│   教学逻辑 + 蒸馏知识 + 问题集 + 应答策略             │
│   → Agent 运行时直接加载                              │
├─────────────────────────────────────────────────────┤
│ Layer 2: Wiki 页面                                   │
│   结构化领域知识（概念、实体、对比、综合）              │
│   → Agent 按需引用，[[wikilink]] 溯源                 │
├─────────────────────────────────────────────────────┤
│ Layer 3: Raw 文档                                    │
│   官方权威原文（PDF、开发指南）                        │
│   → 仅在需要精确引用时读取，不作为日常教学素材          │
└─────────────────────────────────────────────────────┘
```

**各层职责边界**：

| 层 | 存什么 | 不存什么 |
|---|--------|---------|
| Skill | 教学逻辑、应答模板、问题集、抗幻觉规则 | 领域知识本身 |
| Wiki | 概念定义、架构原理、对比分析、数据流图 | API 参数细节、错误码全表 |
| Raw | 完整官方文档、论文原文 | 教学逻辑 |

#### Phase 2 增量：RAG 扩展

**触发条件**（当以下场景在 Phase 1 中频繁出现且 Wiki 无法覆盖时启动）：

| 场景 | 为什么 Wiki 不够 | RAG 解决什么 |
|------|----------------|-------------|
| API 参数查询 | "SetTensorA 的第三个参数在 fp16 和 bf16 下行为不同"——组合爆炸 | 向量化存储 API 文档，精确检索 |
| 错误码诊断 | "RT_ERROR_0x12345 什么意思"——上百个错误码 | 错误码全表索引 |
| 硬件 × 数据类型 × API 组合 | "Atlas A2 上 int8 的 DataCopy 支持吗"——三维组合 | 兼容性矩阵向量检索 |
| 版本差异 | "CANN 9.0 vs 8.0 的 breaking changes" | 版本差异文档索引 |
| 社区长尾问题 | gitee issues 中的非典型问题 | 社区知识向量库 |

## 六、知识运营机制

### 6.1 问题集维护

问题集（Question Bank）是 CannEx 教学质量的核心资产，需持续迭代：

```
反馈闭环：

1. 收集（每次交互自动）
   - 用户原始问题（原文）
   - 命中的画像层级
   - 是否在现有问题集中有匹配
   - 用户满意度信号（继续深问 = 未解决）

2. 沉淀（定期 Review）
   - 未匹配的高频问题 → 新增到问题集
   - 自适应深度偏差的案例 → 调整 Prompt 规则
   - 反复出现的踩坑 → 新增到 :pitfalls

3. 存储结构
   skills/shared/
   ├── question-bank.yaml    ← 问题集（模式匹配 → 知识页映射）
   └── learning-paths.yaml   ← 学习路径定义
   knowledge/pitfalls/       ← 踩坑条目（每条独立知识页）
```

### 6.2 问题集条目格式

```yaml
- id: E1
  level: expert
  question: "有没有先计算 Cube 再计算 Vector 的较好的例子？"
  cognitive_gap: "知道融合概念但缺实现参考"
```
