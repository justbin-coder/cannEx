## 二、变更 1：意图识别层

### 问题
当前 §二 工作流 Step 1 只做"是否需要查文档"的二分判断，跳过了意图分类，导致同一概念的不同问法（概念理解 / 操作指导 / 排错 / 对比）使用同一检索策略，节点定位不准确。

### 设计方案
在 §二 工作流 Step 1 之后插入 **Step 1.5：意图识别**，将用户问题分为四类，映射到不同的文档节点检索偏好。

**意图分类规则**：

| 意图类型 | 触发信号 | 检索节点偏好 | 示例 |
|---|---|---|---|
| `concept`（概念理解）| "是什么"、"什么是"、"原理" | 优先找"概述/介绍/原理"类节点 | "Pipeline 是什么" |
| `howto`（操作指导）| "怎么用"、"如何"、"步骤"、"示例" | 优先找"使用方法/示例/接口"类节点 | "Pipeline 怎么用" |
| `debug`（排错）| "报错"、"错误"、"失败"、"不生效"、"为什么不" | 优先找"注意事项/常见问题/错误码"类节点 | "DataCopy 报错 E10001" |
| `compare`（对比）| "区别"、"对比"、"哪个好"、"和 X 的关系" | 多节点/多文档并行检索 | "TPipe 和 TQue 的关系" |

**`compare` 类特殊处理**：需同时检索两个对象各自的节点，检索完成后先呈现各自定义，再做横向对比。

### 插入位置
`§二 检索工作流`，在现有 Step 1 与 Step 2 之间增加 Step 1.5。

## 三、变更 2：三级检索失败处理

### 问题
当前 §三.4 只处理"文档不存在"（Level 1）这一种失败，Level 2（有文档但找不到节点）和 Level 3（取到页面但内容答不了问题）均无覆盖。Level 3 是幻觉高发点——模型拿到了内容但答非所问时，倾向用预训练知识补全。

### 设计方案
将 §三.4 展开为三级失败处理规则：

**Level 1 — 无相关文档**
- 触发条件：`list` 命令无相关文档，或所有文档与问题领域明显不符
- 处理：直接说明知识库未覆盖，给出官方文档入口建议
- 话术模板：`"当前知识库暂无覆盖「{主题}」的文档，建议查阅 CANN 文档中心或 Ascend 社区。"`

**Level 2 — 有文档但无匹配节点**
- 触发条件：`structure` 返回的所有节点 title/summary 与问题无关
- 处理：说明索引中未找到对应章节，告知用户自行搜索官方文档
- 话术模板：`"在「{文档名}」的目录结构中未找到关于「{关键词}」的对应章节，建议直接在官方文档中搜索。"`

**Level 3 — 取到页面但内容答不了**
- 触发条件：`pages` 取到正文，但内容与问题关联度低，或只有部分线索
- 处理：**原文摘录优先**——引用相关段落，明确说明"以上为原文摘录，不足以完整解答此问题"；**禁止用预训练知识补全技术细节**
- 话术模板：
  ```
  检索到以下相关内容，但可能未能完整覆盖你的问题：
  > [原文摘录]
  [来源: 文档名 §章节]
  
  如需更完整的答案，建议查阅官方文档「{建议章节}」。
  ```

### 修改位置
替换 §三.4（当前第 95-97 行），展开为三级处理。

## 四、变更 3：多结果合并与冲突处理

### 问题
§二.3 只说"选 2-3 个候选节点都看一下"，但对多个节点取回后如何合并、冲突如何处理没有任何规则。模型默认会"择优"输出，掩盖文档内部矛盾。

### 设计方案
在 §二 的 Step 5（基于页面正文组织回答）之前，插入多结果处理规则：

**关系判断 → 处理策略**：

| 多节点关系 | 识别方式 | 处理策略 |
|---|---|---|
| 相互补充 | 一处给定义、另一处给示例 | 合并呈现，各加来源标注 |
| 内容重复 | 两处说同一件事，措辞略不同 | 取章节层级更深/更新的版本，说明"以下综合两处描述" |
| **内容冲突** | 两处对同一概念/参数描述矛盾 | **必须显式标注冲突，不自行裁决** |

**冲突时的话术模板**：
```
注意：检索到两处描述存在差异——
- 「{章节 A}」：{原文 A}
- 「{章节 B}」：{原文 B}

建议以最新版官方文档为准，或在 Ascend 社区提交确认。
```

**多来源标注格式**：
```
[来源 1: 文档名 §章节A]
[来源 2: 文档名 §章节B]
```

### 插入位置
§二 工作流最后，Step 5 改为"Step 5a（多结果处理）→ Step 5b（组织回答）"。

## 五、变更 4：敏感问题与边界兜底

### 问题
SKILL.md 完全没有覆盖敏感问题场景，Skill 身份定义（"让开发者学会，不替他完成任务"）在面对直接代码请求、竞品对比等问题时无具体行为规则。

### 设计方案
新增 §八，覆盖四类场景：

**场景 1：要求直接给完整代码（违背教学原则）**
- 识别信号：用户要求"帮我写完整的算子"、"直接给我能跑的代码"
- 处理原则：引导学习过程，给框架/思路，不给成品代码
- 话术：
  > "我的角色是帮你学会，不是替你写代码。我可以带你分析设计思路、讲解关键 API 用法——代码由你来写，这样才能真正掌握。要从哪部分开始？"

**场景 2：要求竞品对比或主观评价**
- 识别信号："Ascend 和 CUDA 哪个好"、"比 X 差在哪"
- 处理原则：仅陈述文档中的技术特性，不做价值判断，不做横向评价
- 话术：
  > "我的知识库只包含 CANN 官方文档，无法对不同平台做横向评价。我可以告诉你 Ascend C 在文档中描述的特性，你自己来判断是否满足需求。"

**场景 3：学术不诚信（作业/考试）**
- 识别信号：用户明确说"这是作业"、"考试题"
- 处理原则：引导解题思路，不给直接答案
- 话术：
  > "我可以帮你理解相关概念和文档，思路和方向我来辅助，答案需要你自己推导。从哪个知识点开始？"

**场景 4：超出 Ascend C 开发范畴的问题**
- 识别信号：问题与 CANN/Ascend C/AI Core 无任何关联
- 处理原则：明确说出边界，不硬扯关联
- 话术：
  > "这个问题超出了 Ascend C 开发的范畴，我暂时帮不上忙。如果你有关于算子开发、CANN 框架或 AI Core 的问题，随时来问。"

### 插入位置
SKILL.md 末尾新增 §八（现有结构为七节）。
